# SiLEnSeSS rendering benchmarks (#126)

Measurement protocol and tooling for thesis objective **OE3**: stress tests with 100k+ nodes,
**more than 30 FPS with 100k agents on mid-range hardware**, FPS and memory monitoring in the
browser, and a benchmark report.

**Level of detail (LOD, #50) is decided from these results.** It was dropped without data; the
report produced here is the data, and the **LOD preset** (below) measures the candidate
reductions directly. Proposed rule: if, on the reference mid-range machine, a 100k scenario does
not pass (mean FPS > 30) in `idle`, `interaction` or `repaint`, LOD is reconsidered for that case,
starting with the variant that recovers the most frame rate; if every 100k scenario passes, LOD
stays out of scope.

This is a measurement tool, not a user feature. It exists only in **benchmark builds**.

## How the harness is gated

- Compiled in only when the build sets `PUBLIC_BENCHMARK=true` (`bun run bench*`). The flag
  becomes the build-time literal `__BENCHMARK__`; every harness entry point is guarded by it, so
  a normal `rsbuild build` contains no `/bench` route, no harness chunk, no HUD and no probe
  calls (`/bench` is the normal 404 page there).
- A bench build writes to `dist-bench/` (git-ignored), never to `dist/` (what Docker, Vercel and
  CI deploy), and `rsbuild.config.ts` refuses to build with the flag when `CI` or `VERCEL` is set.
- At runtime the harness activates only on `localhost`, `127.0.0.1` or `[::1]`; the preview
  server listens on `127.0.0.1:4100` (the next free port if 4100 is taken — check the terminal).
- `/bench` needs no login and no backend. A fresh clone works as is (the tracked
  `.env.production` holds the public Firebase config). A copy without any `.env*` file also works:
  in bench builds only, a placeholder Firebase key keeps the app shell from failing at startup
  (signing in is then impossible, which `/bench` does not need).

## What is measured

### Benchmark suite — `http://localhost:4100/bench`

Seeded synthetic networks go through the **same pipeline and components as the run view**: the
topology object (same shape as `GET …/topology`) is serialized and `JSON.parse`d (stands in for
the HTTP response parse), handed to the real `SimulationCanvas` (`topologyToData` →
`prepareCosmographData` → Cosmograph, the real layout/freeze timer, clustering and round
repaint), and playback renders rounds through the replay's own chunk path
(`indexChunkBuffer` / `mergeRoundFromChunk` → `store.updateFrame`) at the playback engine's rate.
No backend is involved and no login is needed.

**Synthetic networks mirror the backend's generated runs** (`belief_evolution_simulator`,
`Network.scala` `BuildNetwork`, `FenwickTree.scala`, `Server.scala`, `ApiJson.scala`):

- *density* is the Barabási–Albert `m` (the run's `effectiveDensity`): agents `0..m` form a fully
  connected core; every later agent picks `m` distinct earlier agents with probability
  proportional to an attractiveness score that starts at `m + m·(degreeDistribution − 2)` = `1.5·m`
  (`degreeDistribution` is hard-coded to 2.5) and grows by 1 per pick;
- every attachment is stored in both CSR rows, so a network has `E = m(m−1) + (n−m)·2m` directed
  edges (≈ 2·m·n: 599,988 at 100k agents, density 3), reported as `source` = neighbour (influencer),
  `target` = owner;
- influence weights: per agent, `deg + 1` uniform draws normalised by their sum; initial beliefs
  uniform; agent types in contiguous blocks (4 strategy/effect types), two bias types in blocks;
- at ≥ 10k agents only Administrators can create runs (`maxAgents`), whose `densityFactor` is 1.0,
  so requested density = effective density.

Per-round beliefs are a seeded bounded random walk towards consensus (pull 0.04 to the mean,
noise ±0.03, clamped to [0, 1], 60 % of agents speak each round; silent agents keep their public
belief). Every round recolours every agent. 32 rounds are stored and played ping-pong.

The PRNG is sfc32 seeded through splitmix32. The suite seed (default **126**) and each
scenario's derived seed are recorded in the results; the same seed reproduces the same networks
and rounds. (Cosmograph's own initial layout positions are not seeded.)

**Default matrix** — sizes 10k, 25k, 50k, 100k and 150k (stress) × densities **2, 3, 5**:

- 2 — the wizard's minimum (`density ≥ 2`) and the default template;
- 3 — the second template and the only earlier measurement (100k, density 3, frozen, 60 FPS);
- 5 — a dense case (≈ 1M directed edges at 100k, 1.5M at 150k) that bounds the link cost.

× **3 repetitions**, run repetition-major (each size × density once, then again) so slow drifts
(thermal throttling, background work) spread over all scenarios. Repetitions reuse the same
network (same seed).

**Phases per scenario** (each with a 2 s warm-up and a 10 s measured window unless noted):

| Phase | What happens |
| --- | --- |
| load | generate → JSON parse → `topologyToData` → `prepareCosmographData` → mount → **upload** (layout commit → first frame Cosmograph draws with the data) → layout until the canvas freezes (timings only). |
| `layout` | FPS while the force layout runs **with the data on screen**: from Cosmograph's first simulation tick after its `graphRebuilt` event to the freeze. The upload before it is reported separately (`uploadMs`, its long tasks and longest frame). The product's freeze timer (`LAYOUT_DURATION_MS` = 5 s) counts from the layout commit and is unchanged, so this window is shorter than 5 s by the upload; its actual length is recorded (`actualMs`). |
| `idle` | frozen canvas, no input. |
| `interaction` | scripted camera through the Cosmograph API: every 1 s one step of fit → zoom in ×4 → pan → pan → zoom out → pan (600 ms animations, pan targets from the seed). |
| `repaint` | timeline playback: `playhead += dt × 10 rounds/s × speed`, one store frame per new round, `playbackActive` on (as in the run view). Default speeds ×1 (10 rounds/s) and ×16 (a new round every frame at 60 Hz, the upper bound for every speed ≥ ×16). Each round is also timed (see *Repaint breakdown*). |
| `cluster-layout` | grouping on (default "strategy"): from the first frame drawn with the clusters (first tick after the last `clustersUpdated`) until the product re-freezes 4 s after the change; the cluster update before it is the phase's `lead`. |
| `cluster-idle`, `cluster-interaction` | idle and scripted camera with the grouping on. Grouping is then removed (2 s de-cluster). |

Before the matrix, an unmeasured **pre-warm** network (500 agents, density 2) is loaded: the first
`prepareCosmographData` of a page also downloads and compiles DuckDB-WASM, which would otherwise
inflate the first scenario's load (its timings are kept in the result as `prewarm`). The canvas
is unmounted (Cosmograph destroyed, store reset) after every scenario, then a 2 s settle pause
runs before the next. All of the above is configurable on the page (sizes, densities, phases,
speeds, cluster mode, canvas variants, warm-up, window, repetitions, settle, seed, canvas size),
and the page shows a reproducible URL, e.g.
`/bench?sizes=100k&densities=3&reps=3&phases=idle,repaint&speeds=1,16`. `&autorun=1` starts it.

**Estimated duration: default suite ≈ 69 minutes** (45 scenarios × ~1.5 min); **LOD preset ≈ 68
minutes** (27 scenarios; ≈ 95 minutes with `repaint` ×1 added). The page shows the estimate of
the current selection and of both presets.

### LOD preset — `http://localhost:4100/bench?preset=lod`

50k, 100k and 150k agents × densities 2, 3, 5 × 3 repetitions; `idle` and `interaction` (add
`repaint` on the page or with `&phases=idle,interaction,repaint` to include ×1 playback). Each
scenario is loaded once; after the baseline it is measured again with each canvas variant:

| Variant | What changes | How |
| --- | --- | --- |
| `baseline` | nothing — the product as shipped | |
| `links-transparent` | the product's own "hide links" toggle: link colour made transparent, `renderLinks` stays true | canvas state |
| `links-off` | `renderLinks: false` | canvas config overlay |
| `straight-links` | `curvedLinks: false` (1 segment per link instead of `curvedLinkSegments` = 19) | canvas config overlay |
| `one-link-per-pair` | one of the two reciprocal edges of every pair (half the links) | the canvas is reloaded with the deduplicated data |

The variants are switched through the bench-only canvas probe, which drives the canvas' own state
(`linksHidden`, its config overlay); nothing changes in normal builds.

**Reciprocal edges.** Generated networks store every attachment as A→B and B→A (one per CSR row),
and Cosmograph draws every directed edge as its own link. With curved links, cosmos.gl places the
control point at `midpoint + perpendicular(B − A) · |B − A| · h` (its line vertex shader), so the
reverse edge bends to the opposite side: each pair is drawn as **two distinct arcs** (a lens), each
`curvedLinkSegments` = 19 segments. The link work of the vertex stage and the pixels drawn are
therefore about twice those of one link per pair; `one-link-per-pair` measures how much frame rate
that costs, and `links-transparent` versus `links-off` whether transparent links are still paid for.

### Metrics

Per phase, from `requestAnimationFrame` deltas:

- **Mean FPS — the headline and the pass/fail criterion**: frames delivered / measured seconds.
  On a vsync-locked display every frame time is a multiple of the refresh interval, so FPS values
  are quantized to `refresh / n` (165 Hz → 165, 82.5, 55, 41.25, 33, 27.5…): the median jumps
  between those levels (a network can read 41.25 or 27.5 with nothing in between) while the mean
  moves smoothly with the work. **PASS = mean FPS strictly greater than 30.**
- **1% low** = 1000 / p99 frame time, and p5 FPS = 1000 / p95 frame time (linear interpolation
  between order statistics); the median FPS is kept as a secondary column;
- share of frames slower than 33.3 ms, frames slower than 50 ms, dropped frames estimated from
  the measured refresh rate, max frame time;
- long tasks (`PerformanceObserver('longtask')`, Chromium): count, total and max duration. When
  nothing runs in JavaScript (frozen idle), long tasks mean the main thread is waiting on the GPU
  (WebGL calls block once the GPU falls behind);
- JS heap (`performance.memory`, Chromium): min / max / end over the window (sampled every 250 ms);
- page memory via `performance.measureUserAgentSpecificMemory()` right after the `idle` window
  (it resolves on the browser's next GC, so it is not called inside the window; up to 10 s) when
  the page is cross-origin isolated (`bun run bench:isolated`), otherwise recorded as `unavailable`;
- **GPU memory: an estimate, not a measurement** — a model of the buffers cosmos.gl allocates
  (point-state textures, link-force textures, per-link and per-point vertex buffers, screen
  buffers; see `src/features/benchmark/lib/gpu-estimate.ts`);
- load timings (also as `performance.measure` entries `bench:<scenario>:*` in DevTools), and a
  per-scenario `timeline` of the canvas / Cosmograph lifecycle events;
- the **GPU the canvas actually drew with** (`canvasRenderer`: the renderer of Cosmograph's own
  WebGL context), compared with the environment probe; a mismatch is recorded as a warning.

### Repaint breakdown (where the per-round cost goes)

Per round the playback pushes one frame to the store (`updateFrame`); the canvas re-renders and
hands Cosmograph new colour/size functions; Cosmograph's `setConfig` then re-queries the point
table from DuckDB-WASM (a worker), recomputes every colour and size in JavaScript and uploads them
(`pointColorUpdated`). For every round inside the window the suite records:

- **merge** — the replay merge of the round (`mergeRoundFromChunk`, wire parse);
- **store → commit** — `updateFrame` until the canvas committed the frame (React render);
- **Cosmograph update** — each `setConfig` call from the call until it settled (query, colours,
  sizes, upload); its synchronous part separately;
- colour updates, long-task time per second, mean frame time.

Read it with the `idle` row of the same network: idle frame time is the drawing cost with
nothing changing; what the repaint frame adds on top is the per-round update. If the Cosmograph
update per round is of the order of the repaint frame and long tasks fill the window, the cost is
CPU/JavaScript (and the DuckDB round trip); if the repaint frame barely exceeds the idle frame,
the cost is the GPU drawing. The report also fits frame time on agents and links together: a
large per-agent term in `repaint` (and not in `idle`) points at the per-point JS update.

### Debug HUD on real runs (run view, bench builds only)

Open any run in the run view of a bench build and press **Shift+H** (or the "FPS HUD" button):
live FPS (current, mean, 1% low, median and p5 over 5 s), slow/dropped frames, JS heap,
agents/edges (and the inferred density), the load timings of the network (topology fetch, its
network part from Resource Timing, JSON parse, `topologyToData`, `prepareCosmographData`, mount,
upload until the first frame with the data, layout until freeze; "topology fetches: 2" means a
concurrent duplicate fetch ran; the first network of a page also pays the DuckDB-WASM cold start
in `prepareCosmographData`), and the environment. **Copy metrics** puts a JSON snapshot on the
clipboard; **Record 10 s** measures one phase with the suite's statistics and offers it as
JSON/CSV (same schema, `source: "real-run"`; the live readout pauses while recording). The HUD
re-renders 4×/s while open — close it for idle readings.

## Protocol

### 1. Machine

- Use a **normal desktop browser running natively** on the target machine (Windows, macOS or
  Linux desktop). **Not** a browser inside WSL, a VM, remote desktop or a headless browser: they
  use software rendering (SwiftShader / llvmpipe), which the harness detects, flags and the
  report excludes.
- Chrome or Edge (Chromium) is the reference: it exposes `performance.memory` and long tasks.
  Firefox/Safari still give FPS and timings. Record the browser and its exact version.
- Keep the machine **online**: Cosmograph loads DuckDB-WASM (its worker and `.wasm`) from
  `cdn.jsdelivr.net` the first time a page prepares data. Without it, `prepareCosmographData`
  never resolves and every scenario fails with "canvas did not freeze".
- Power plugged in, battery saver off, OS power mode "balanced" or "best performance" (write down
  which). Close other applications and browser tabs; no downloads, updates or video calls.
- Browser window maximized on the display you record, at 100 % zoom. Do not use the computer
  during the run, and keep the tab visible (a hidden tab throttles frames; the page records it as
  a warning in the results).
- Optional Chrome flags (record them if used): `--enable-precise-memory-info` (otherwise
  `performance.memory` is coarse/quantized), `--js-flags=--expose-gc` (forces a GC before each
  scenario; recorded as `forcedGc`).

**Record about the hardware** (the page captures GPU renderer, CPU threads, device memory —
rounded and capped by the browser —, browser, platform, screen, DPR, viewport and refresh rate;
write the rest down) and keep it next to the results, e.g. in the commit message or a
`machines.md`:

| Field | Example |
| --- | --- |
| Machine id (file prefix) | `laptop-ref` |
| CPU model, cores / threads | Intel Core i5-1135G7, 4 / 8 |
| GPU model + driver version | Intel Iris Xe, 31.0.101.4502 |
| RAM | 16 GB DDR4-3200 |
| OS + version | Windows 11 23H2 |
| Display: resolution, refresh, scaling | 1920×1080, 60 Hz, 125 % |
| Browser + version | Chrome 130.0.6723.70 |
| Power state / power mode | plugged in, balanced |

### 2. Running on another machine

Prerequisites: [Bun](https://bun.sh) 1.1 or newer and Git, a desktop Chromium browser.

```bash
git clone <repo> && cd front_BES      # or pull, or copy the folder (keep .git and .env.production)
bun install
bun run bench                         # build into dist-bench/ and serve on 127.0.0.1:4100
```

- Works natively on Windows (PowerShell or cmd): `bun run` executes package scripts with its own
  shell on Windows, which understands the `PUBLIC_BENCHMARK=true rsbuild …` form the scripts use
  (checked with `bun --shell=bun run bench` — the same shell — building into `dist-bench/` and
  serving). In WSL, run the commands there and open the page in the Windows browser.
- No `.env` is needed (see *How the harness is gated*). A copy without `.git` builds too, but the
  results then show the commit as `unknown`: prefer a clone or keep `.git`.
- Open `http://localhost:4100/bench` (the terminal prints the actual port).
- **Laptops and hybrid graphics**: make the browser use the dedicated GPU. Windows: Settings →
  System → Display → Graphics → add the browser (`msedge.exe` / `chrome.exe`) → "High
  performance"; then restart the browser. Check `edge://gpu` / `chrome://gpu` ("GL_RENDERER") and
  the page header: it shows the GPU of the environment probe and, after the first scenario, the
  **canvas GPU** (the context Cosmograph actually draws with). A mismatch is also written to the
  result's warnings. On a laptop without a dedicated GPU, record the integrated GPU and keep the
  power adapter connected.
- Name the result files per machine: `benchmarks/results/<machine-id>__bench-<date>-<commit>.json`
  (e.g. `laptop-igpu__…`, `pc-rtx2060__…`), and fill in the hardware table above for each one.

### 3. Run the suite

```bash
bun install
bun run bench          # optimized production build into dist-bench/ + preview on 127.0.0.1:4100
```

(`bun run bench:build` / `bench:preview` split the two steps; `bun run bench:isolated` serves
with COOP/COEP so `measureUserAgentSpecificMemory` works — the Google login popup does not work
there, so use it for the synthetic suite only.)

Open `http://localhost:4100/bench`, check the header (version, commit, "production build", GPU),
keep the defaults (or select a subset, or the **LOD preset**), **Start suite**, wait, then
**Export JSON** (and CSV if you want it). Measure only this optimized build: React's development
mode distorts FPS (`bun run bench:dev` exists for working on the harness itself and its results
are excluded from the report).

### 4. Validate against real runs (optional, needs your local backend)

The bench build is a production-mode build, so it takes `PUBLIC_BACKEND_URL` from
`.env.production` like the deployed image. To point it at your local backend, set the variable
for the build — shell variables win over `.env` files:

```bash
PUBLIC_BACKEND_URL=http://localhost:<backend-port> bun run bench
```

With the backend running locally, open the bench build at
`http://localhost:4100`, log in, create or open a generated run (e.g. 100k agents, density 3),
open a network, press **Shift+H**, wait until the canvas freezes, then **Record 10 s** (idle);
start playback and **Record 10 s** again; **Download JSON** for each. Compare with the synthetic
100k / density 3 rows. The real run view also re-renders the timeline and charts on every round,
which the synthetic suite does not.

### 5. Store the files

Put the exported JSON files in `benchmarks/results/`, prefixed with the machine id (see above).
Commit them. Do not commit results from headless/WSL browsers or development builds.

### 6. Aggregate

```bash
bun run bench:report   # = bun benchmarks/scripts/aggregate.ts
# options: --results <dir> --out <dir> --threshold 30 --include-dev --include-software
```

It validates `schemaVersion` (1 and 2 are read) and the harness marker of every
`results/*.json`, skips invalid files, excludes development builds and software rendering
(unless asked), groups results **per machine** (GPU · CPU threads · platform · browser) and
writes `benchmarks/report/`:

- `summary.md` — per machine: environment, builds and the GPU the canvas used; a table per size
  × density × phase with links, rendered entities (agents + links drawn), repetitions, **mean
  FPS**, 1% low, p5, median, share of frames > 33.3 ms, heap max, GPU estimate and **pass/fail
  (mean FPS > 30)**; **frame rate vs rendered links** for idle, interaction and repaint ×1
  (ordered by links, with a least-squares line of mean frame time on links over the points that
  are not capped by the display refresh, the link count where it crosses 30 FPS, the last
  passing / first failing link counts, and a two-factor fit on agents and links); the **canvas
  variants** table (mean FPS and change versus baseline); the **repaint breakdown**; load timings
  (with the upload) and failed scenarios;
- `summary.csv`, `load.csv` — the same tables as CSV; `links.csv` — mean FPS / frame time
  against links drawn, for plots; `phases.csv` — every scenario × phase row.

Values are medians over repetitions (heap: the maximum). Results of schema version 1 (the first
campaign) are reported too; their `layout` / `cluster-layout` windows started at the layout
commit, before the data upload, so they are marked "n/c" (not comparable) and not judged.

## Result files

One JSON document per suite run (or HUD recording): `schemaVersion` (2; 1 is still read),
`harness` (`"silensess-bench-harness"`), `kind` (`suite` | `hud-record`), `id`, `startedAt`,
`finishedAt`, `complete`, `build` (mode, app version, git commit and dirty flag, build time),
`environment` (GPU vendor/renderer and how it was read, threads, device memory, user agent and
client hints, screen, DPR, viewport, refresh estimate, cross-origin isolation, API support),
`config` (the full suite configuration, canvas timings, reproducible query), `warnings`,
`prewarm` (the unmeasured pre-warm load, or null), and `scenarios[]` — each with agents, edges,
density, repetition, seed, stage size, status/error, `load` timings (with `uploadMs` and its long
tasks), `gpuMemoryEstimate`, `canvasRenderer`, `timeline`, `variantLoads` (the one-link-per-pair
reload) and `phases[]` (canvas variant, links in the data / drawn, frame summary, long tasks,
heap, UA memory, the excluded `lead` of layout windows, repaint rate and per-round breakdown).

## Known limitations

- rAF deltas measure the main thread's frame cadence; GPU work that the browser pipelines can
  hide behind it. This is the standard browser-side FPS measure, and the one users perceive.
- The canvas size changes the fill cost: the suite uses a fixed 1280 × 720 CSS px canvas by default
  (recorded with the DPR); the real run view's graph panel depends on the window.
- The synthetic repaint excludes the network fetch of frame chunks (the real replay downloads
  ~8 MB chunks) and the run view's other per-round re-renders; use HUD recordings for those.
- The force layout is time-boxed by the product: the 5 s freeze timer starts at the layout commit,
  so a slow upload eats into it (with software rendering the upload took ~8.9 s and the layout ran
  for ~0.3 s before the freeze; the timer itself fired late because long tasks blocked the main
  thread). The `layout` window is therefore what remains after the upload, recorded with its
  actual length.
- `deviceMemory` is rounded and capped by browsers; GPU memory is an estimate.
